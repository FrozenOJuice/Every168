# Revisions, atomic commands and consistent reads

Every mutable Core record exposes an integer `version`. Edits, archives and deletes require its last-seen value in `If-Match: "<version>"`. Missing/invalid preconditions return 428; stale revisions return 409 `STALE_REVISION`; missing or foreign records return 404. Single-row repositories compare-and-swap atomically. Workout/cardio services lock the owned parent and check its revision before changing the aggregate and time ledger. Revisions are required for internal service callers too.

PostgreSQL advances revisions on every update, including foreign-key `SET NULL`. The migration's triggers also prohibit reassignment of record identity/creation metadata and modification of food snapshots. These triggers are intentionally maintained as SQL in migration 0006; Drizzle models the columns, checks, uniqueness and foreign keys. Numeric bounds reject non-finite values. Checks enforce Core status/type values, source-kind/ID pairs, valid intervals and ordered child positions. Composite owner foreign keys cover activity-to-plan links; existing single-column `SET NULL` foreign keys supply the detach behavior. Definitions remain archived rather than deleted.

Every domain HTTP mutation also requires a UUID `Idempotency-Key`. A small infrastructure service owns the command transaction and a repository owns its `write_receipts` table. UUID keys are normalized to lowercase; a transaction-scoped advisory lock serializes the same user's key. The receipt contains a hash of the normalized method/path/input/revision and the successful JSON response. Different requests sharing a committed key return 409 `IDEMPOTENCY_CONFLICT`. Equal keys belonging to different users are independent. The domain effect and receipt commit together, and exercise/planning reuse that same opaque transaction scope. A failed transaction leaves neither. Replays return the original result even after a server restart or subsequent record deletion.

Routes still validate contracts and call domain services. This command boundary handles transaction/replay mechanics only; it does not choose domain repositories or implement business rules. Auth uses its existing transactional library boundary and is excluded from receipts. No write retries run automatically on the server.

The API client retains the exact in-flight payload for a request key. Forms and quick actions retry that intent after an uncertain network/5xx response, including any originally generated timestamp. A confirmed new action gets a new key even if its values are identical. Stale edits retain local input and offer an explicit reload. Workout query refreshes no longer remount an unsaved editor; its revision advances only after a successful save. Preferences likewise retain the revision used to initialize the form.

Workout aggregate reads and the planner's block/entry dataset use read-only repeatable-read transactions. Food logging holds a shared lock on its definition while validating archival state and copying its snapshot. Exercise definition and planned-block reference reads take shared locks during write transactions. Deletes/checks serialize with these reads; lock/deadlock timeouts roll back rather than partially saving.

Limits are deliberate: receipts remain until account deletion or a development reset, so storage grows with writes. Pending client retry handles live in the current form/action; closing the form, navigating away or reloading loses that handle, so review history before manually repeating an uncertain action. This is not offline synchronization. Dashboard panels/category labels may reflect adjacent committed reads; the planner accounting dataset and workout aggregates are consistent. Polymorphic activity/source lifecycle rules remain owned by the transactional services, backed by the unique source index and source-kind check. Direct maintenance SQL must respect those lifecycle rules. Existing development/test data is disposable; no backfill or compatibility layer was added.
