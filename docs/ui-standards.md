# Core UI standards

The owner approved a calendar-first home after backend hardening. This document records the implemented UI direction; feature slices should follow it when extending their workflows.

Use the normal arrow cursor for disabled actions, including saves and toast actions. Never use wait or progress cursors; communicate pending work through visible status and disabled controls.

## Navigation and information hierarchy

- Calendar (`/`), Fitness (`/fitness`), Food (`/food`), Tasks (`/tasks`) and Assistant (`/assistant`) are the current primary destinations, in the slim desktop sidebar and mobile bottom navigation. Keep the account control available. Unscheduled, Routines, and Goals are retained outside navigation for later decisions; the old Exercise UI is removed. Fitness has Training, Exercises and History views in the main column and the shared Day panel on the right.
- Account disclosure: identity, Settings, Sign out. Keyboard Escape closes it and restores focus. Settings contains preferences and categories.
- Calendar is the central general planner. Date and Day/Week/Month view live in URL query parameters. The old `/week` URL redirects to Calendar. Food moments open their local-date Food log; workout activity opens its Fitness session.
- Domain workspaces omit a visible domain-name title bar; retain an accessible page heading and put view navigation and actions with the main content. Calendar uses an integrated top toolbar so its grid fills the workspace. Domain reporting and tracking controls belong inside their domains.
- Calendar has no details toggle or extra settings/summary/Today panel beneath it. Compact tools/search dialogs and selected-date quick actions are authorized; reporting surfaces remain in their domains.

- Food, Fitness and Tasks use `DomainDayPanel` with Calendar's date picker, activity cards and next-plan emphasis. Use the shared --calendar-side-width token (350px) for Calendar’s activity rail, its date toolbar area, and domain rails/drawers; drawers fit narrower viewports. Keep the full-viewport-height right rail aligned to the workspace top on wide screens and a Day drawer at 1150px and below. Calendar itself does not mount an additional domain panel.
- Start the panel with one selected-date control and previous/next arrows, matching Calendar’s plain date button without an extra chevron and reusing its control styling. Share --calendar-date-font-size: 1.25rem by default, 1.125rem at 700px and below, 0.8125rem at 360px and below; clicking it opens the shared date picker. Omit a separate Your day rail header and duplicate date line; retain the labelled drawer heading and close control. Use one full-width outlined Open Calendar navigation button in the footer, with a Calendar icon, centred label, forward arrow and a minimum 44px target. Stack any domain action above it. Place Today, using the same shared outlined button style as Calendar, beside the domain/All activities filter. Use two-letter weekdays in the week strip, respecting account timezone/week start. Carry the selected date across client navigation between domains; explicit valid URL dates take precedence. Keep date changes within the current workspace without discarding edits.
- Default to the domain's genuine activity and linked plans; offer All activities for the broader day. Name the domain in its empty state so it does not imply the whole day is empty. Domain adapters supply source actions and canonical plan links. Never infer domain ownership from titles or categories. Open the full Calendar on the selected date and guard unsaved changes before navigating away.
- Keep the Next highlight as a summary and retain that same activity in Coming up, so the chronological list remains complete. Omit standalone Planned labels above timed plan cards; retain recorded activity details and the Next summary’s Planned prefix. Reuse Calendar’s actual activity-list headings, cards, spacing and selection styles; do not reduce their typography in domain rails. Timed/all-day plans use shared Calendar selection, editors, repeating-scope prompts and history-backed deletion/Undo/Redo. Place selection controls below the list, sticky within its scroll area, so selecting does not move a card before a double-click. Retain accessible Actions and keyboard selection/editing. Scope Day keyboard shortcuts to its own activity region, preserving other domain editors’ shortcuts.
- The domain Day action row has no section divider or generic Calendar actions label. Show selection count and Actions only for selected plans; otherwise expose available Undo/Redo directly.
- Portal shared editors, menus, scope prompts and feedback within the active Day drawer or page landmark. Block native drawer dismissal and day/filter changes while commands or forms are pending/uncertain. Keep mounted interaction state when a background read fails, showing retry feedback alongside stale data. Recorded activity retains source-specific actions; removing planned time preserves reusable definitions and recorded history, and Undo restores links. Retained preview launchers must not cover selection actions. Day-drawer toasts sit above the bottom selection and footer controls.
- Keep Day independent of domain tools, with no Day/Exercises switch. Fitness places library browsing in the Exercises tab; the shared workout editor retains its adjacent library. Add exercise opens an inline picker with its search focused; selecting returns to the retained workout. Exercise names and View history controls open shared details/history in context. New domains reuse the rail/drawer convention while keeping their own workflow in the main area.

## Calendar behavior

- View controls appear as Day, Week, Month; Week is the default on every viewport. Add, Search and More sit on the left of the top toolbar; Day/Week/Month is centered; Today sits immediately left of the previous-date arrow on the right. Previous and next occupy fixed positions in a compact date group, stepping by the active view; give the title button a generous minimum width with small gaps to the arrows, and let longer dates use available center space without moving either arrow. Center the single date line vertically between the arrows at the same center position in every view. Week/Month show the full month/year; Day shows the full month/day/year at exactly the same font size. The full weekday appears as a small label at the top of the Day activity sidebar, outside the date control. Use hover/focus feedback rather than a chevron. Clicking opens an anchored nonmodal mini calendar (Day/Week, respecting week start) or month grid with year navigation (Month), with Escape/outside dismissal. Wide Day view aligns the date area and divider with its activity sidebar. Calendar fills the workspace between the left sidebar and the browser edge, with no outer card border or rounding; narrow screens fill the space between the fixed navigation bars.
- In the Week date picker, each week is one selectable row. Fill the selected row continuously. Across Day, Week and Month pickers, outline unselected options on hover; keyboard focus also receives a visible outline.
- Date dropdowns have no close X. Selection, outside click and Escape dismiss them.
- The Month date dropdown shows all twelve months in a three-column, four-row grid beneath its year controls, with month buttons at least 48px tall.
- Center each date dropdown under its title button in Day, Week and Month. Reduce dropdown width on narrow screens so it remains centered and fully visible.
- Week and Day share a 24-hour time grid at 60px per hour, with five-minute snapping. Today starts near the current time; other selected dates start at 07:00. Scrolling is remembered in page memory across periods and views; Today resets it to the current time. Week keeps seven readable columns in a contained scroller on smaller screens, initially revealing the selected date. Week headers and the time axis stay visible; Day omits its duplicate weekday/date header. The date title opens a date picker, and a live marker follows the account timezone without moving the scroller each minute.
- View tabs navigate using the selected calendar date when present: a selected Month day opens its Week or Day, and a selected five-minute Week slot opens its Day. Without a selection, the viewed date remains the target. Navigation clears the selection.
- The Day and Week time column adjusts hour spacing by vertical drag: down spreads hours apart and up compresses them. Zooming out from a scrolled position keeps its scroll fraction steady, reaching the full-day fit without a pivot jump; zooming in keeps the time under the pointer steady. The visible minimum fits the 24-hour grid exactly to the available height, with 24:00 at the bottom of the time axis beside the closing line; ordinary labels are vertically centered on their lines while 00:00 and 24:00 stay inside the boundaries. 60px per hour is the default and 240px is the maximum. Double-click the column or press R while using Day/Week to reset; the shortcut ignores text fields and open editors. Arrow and Page keys provide keyboard adjustment when the axis is focused. At 150px/hour, labels and guides switch to 15-minute intervals; at 90px/hour, to 30-minute intervals; at 36px/hour, to two-hour intervals; and at 20px/hour, to four-hour intervals. Return thresholds of 140px, 84px, 42px and 26px prevent flicker while dragging. The full-day fit follows viewport and Day/Week layout changes. The scale and mark interval are remembered per account in this browser. All time-grid positions and five-minute interactions use the chosen spacing; Month has no time scale.
- Selecting the grid prefills creation in five-minute increments; hover previews show the selected time. Keyboard users use Add block or focus an existing record to edit. The editor offers 15/30/60/120-minute durations. Changing Start preserves elapsed duration across dates and clock changes; changing End sets a new duration. Invalid or ambiguous local times remain editable and must be resolved before saving.
- Month follows the preferred week start and fits all seven columns and four to six week rows inside the available viewport without horizontal or vertical scrolling. Put dates at the top right with a 24px circle. Show up to four thin event rows when space permits; reserve an overflow row when needed, so five or more show at most three previews and “+N more”, opening Day view for that date. Use 20px rows for fine pointers and 24px for touch, preserving single-line titles and right-aligned start times. Reduce previews with available height; narrow cells show compact counts, and very short rows place the count beside the date using a 20px date circle. Moments retain separate access except in very short rows, where the Day-view count includes them. Single-click selects a day, Add creates at its current account-local hour, and double-click/Enter opens a draft. Date/view changes survive reload and browser history; month arrows clamp at shorter month ends.
- Plans and actual entries appear together, with solid/dashed borders, a legend, and explicit accessible labels. Linked records remain separate entries at their real times and accessible from the editor; no plan is inferred to be completed. API summaries still account for planned and recorded time separately.
- Short records receive usable targets with title/time priority, and colliding targets occupy separate lanes. Week displays two lanes per overlap group; excess records are accessible through a count button in the day header. Other records stay on the grid. Day permits every lane with contained scrolling. Overnight continuations show an end-time/continuation label. Clock-change days use an ordered list in Day with explicit zone labels for repeated/missing hours.
- Calendar editors omit Category and Goal; creation, saved-plan editing and duplication show notes directly. New blocks are plans only, without a Record choice or Log actual block action. Category filtering, block category labels/colors and the create-goal shortcut are absent, and Calendar does not fetch category/goal selector lists. Duplicate opens a draft for the following local date with the saved title, notes and duration. Existing stored references survive ordinary edits. Nothing is created until Save; recorded time and identity/revision fields are never copied. New or moved plans reveal their saved date/time. Recorded activity remains visible and links to its source domain. Domain logging remains in Quick actions and domain pages. Search/filter and quick actions live in compact top controls and dialogs; the lower summary/health panel remains removed.
- Month loads at most six existing week endpoints through the typed API client. A failed week has a retryable error, never a false empty calendar. Editing invalidates the same week caches across every view. Date-only plans load separately for the same bounded visible range. Their sticky row, Month previews and day lists keep them outside timed allocation.

## Visual standards

- Use the exact eleven semantic color tokens in `168HOURS_BUILD_SPEC.md`. Never alter the palette to create a new visual theme. Category colors are organizational hints accompanied by names.
- Use system sans-serif fonts. Body text is 14px; page titles scale from 26–32px, section headings are about 17px, form labels 13px. Calendar cells use compact type and expose full information in their editor or Day view.
- Use a 4px spacing rhythm, principally 8/12/16px within groups and 24/32px between sections. Common controls and panels use an 8px radius; dialogs use 12px. Borders and spacing establish groups; shadows are reserved for overlays.
- Use the green primary button for the main action, bordered buttons for secondary actions, and destructive text for deletes. Controls should have 44px touch targets; avoid hover-only actions.
- The muted foreground on the muted background falls below 4.5:1 contrast. Use foreground text on muted controls, or put muted text on card/background surfaces.
- Share base styles in `app/globals.css`; shell, calendar and existing domain styles are separated under `styles/`. Keep feature behavior in feature components, separate from layout and styling.

- Search selectors dismiss and release focus on one pointer click outside the actual field/options, including nearby layout gaps. Chip removal must not reopen search; keep keyboard focus on a remaining chip or a closed search field. Preserve associated-label focus and deliberate option selection.
- Persistent labels, explicit units, inline validation, visible busy state and a clear save action are required. Dialogs use the native modal element, a labeled heading, a close control and Escape dismissal. Closing restores focus to the opener when it still exists, without scrolling the page.
- Use the shared Toast/useToast component for brief feedback across domains, with success/info/error states, a short message, at most one action and a dismiss control. Place it bottom-right above navigation and fixed form actions; preserve fullscreen dialog portals. Success lasts 2.4 seconds, information/errors 4 seconds and actionable messages 5 seconds, paused on hover or keyboard focus. Use live announcements and reduced-motion styling. Toast expiry must not discard records or drafts; keep important actions reachable afterward. Field validation and unresolved conflicts/storage failures remain inline.
- Keep drafts on recoverable/stale-save errors. Preserve the shared Form/useCommand revision and idempotency behavior. An uncertain write exposes an explicit retry of the same intent. Do not silently substitute a newer revision.
- Confirm deletes. Source-backed time must be edited through its source activity; deleting a plan retains recorded time.
- Show useful empty, loading and recoverable error states. Do not invent statistics or treat missing measurements/nutrients as zero.
- Scope browser verification to the workflows changed. Check desktop, phone and tablet layouts, keyboard navigation, overflow, accessibility, ownership, save failures and complete user flows.
